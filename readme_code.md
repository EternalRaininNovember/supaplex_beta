## 1. Общая схема

Скрипт сам не моделирует игру. Всю игровую логику выполняет настоящий движок OpenSupaplex,
собранный как консольная утилита без окна. Скрипт только запускает её и упаковывает результат.

```
 demo.SP ──▶ supaplex-dataset.exe ──▶ временный .spds ──▶ read_spds() ──▶ dict numpy ──▶ .npz
            (движок игры, C)          (сырые шаги)        (Python)                       (np.savez_compressed)
```

| Функция | Строки | Роль |
|---|---|---|
| `step_dtype` | [66–75](supaplex_dataset.py#L66-L75) | описание одного шага в сыром файле как numpy-структуры |
| `read_spds` | [78–124](supaplex_dataset.py#L78-L124) | сырой `.spds` → словарь массивов эпизода |
| `load_episode` | [127–130](supaplex_dataset.py#L127-L130) | `.npz` → словарь массивов (для кода обучения) |
| `find_demos` | [134–149](supaplex_dataset.py#L134-L149) | собрать список демо из файлов, масок и папок |
| `episode_name` | [152–157](supaplex_dataset.py#L152-L157) | имя `.npz` по пути демо |
| `build_one` | [160–177](supaplex_dataset.py#L160-L177) | одно демо → один `.npz` |
| `command_build` | [180–213](supaplex_dataset.py#L180-L213) | команда `build`: параллельная обработка всех демо |
| `command_info` | [216–228](supaplex_dataset.py#L216-L228) | команда `info` |
| `command_preview` | [231–261](supaplex_dataset.py#L231-L261) | команда `preview`: GIF/PNG из кадров |
| `main` | [264–288](supaplex_dataset.py#L264-L288) | разбор аргументов, выбор команды |

## 2. Откуда берутся данные: supaplex-dataset.exe

Это не Python, но без понимания утилиты непонятен формат, который читает скрипт.
Исходник: `D:\git_repo_src\open-supaplex\tools\supaplex-dataset.c`.

**Как утилита встраивается в игру.** Она делает `#include "../src/supaplex.c"` и подменяет функцию
`updateKeyboardState` своей (`updateKeyboardStateForDataset`). Игра вызывает опрос клавиатуры ровно
один раз в начале каждого игрового кадра, до любой игровой логики. Поэтому подменённая функция
вызывается на границе кадров, и в этот момент видно состояние «до решения игрока».

**Как она запускает игру.** Утилита вызывает `main` игры с ключом `-q <демо>`: демо проигрывается
без ограничения скорости, но каждый кадр всё равно рисуется (в память, окна нет). Ключ `-u` не подходит:
он пропускает отрисовку, и кадров экрана не было бы.

**Что происходит на каждом кадре:**

```
начало кадра t:
    flushPendingStep(gCurrentUserInput)   # записать шаг t-1, его действие теперь известно
    captureObservation()                  # запомнить наблюдение t: сетку, экран, скаляры
... игра читает ввод из демо (gCurrentUserInput = действие t) и обновляет мир ...
```

Действие кадра `t` становится известно только после того, как игра его прочитала. Поэтому наблюдение
кадра `t` держится в памяти (`sPendingStep`) и записывается в файл в начале кадра `t+1`. К этому моменту
`gCurrentUserInput` ещё хранит действие кадра `t`. Последний шаг дописывается после выхода из игры.

**Что попадает в шаг:**

| Поле | Откуда в игре |
|---|---|
| `frame` | `gFrameCounter` |
| `action` | `gCurrentUserInput` (значения > 9 заменяются на 0, см. [тонкие места](#10-тонкие-места)) |
| `flags` бит0 «погиб» | `gQuitLevelCountdown != 0` и уровень не пройден |
| `flags` бит1 «пройден» | `byte_5A19B` (флаг успешного прохождения) |
| `flags` бит2 «гравитация» | `gIsGravityEnabled` |
| `infotrons`, `red_disks` | `gNumberOfRemainingInfotrons`, `gNumberOfRemainingRedDisks` |
| `murphy` | `gMurphyLocation` — индекс клетки `y * 60 + x` |
| `grid` | `gCurrentLevelState[i].tile` и `.state` для всех 1440 клеток |
| `screen` | копия `gScreenPixels` — экран 320×200 в индексах палитры |

Код возврата утилиты: 0 — демо прошло уровень, 1 — не прошло, 2 — ошибка.

## 3. Константы

[Строки 52–63](supaplex_dataset.py#L52-L63).

```python
LEVEL_SIZE = 1536                              # размер уровня в LEVELS.DAT
LEVEL_WIDTH, LEVEL_HEIGHT = 60, 24             # поле в клетках
SCREEN_WIDTH, SCREEN_HEIGHT = 320, 200         # экран игры
FILE_HEADER_SIZE = 16 + LEVEL_SIZE + 16 * 3    # заголовок 16 байт + уровень + палитра (16 цветов × RGB)
TRAILER_SIZE = 9                               # "SEND" + u32 число шагов + u8 решён
```

`ACTION_NAMES` — названия действий, индекс равен коду действия (0 = `none` … 9 = `space`).

`DEFAULT_GAME_DIR` вычисляется от расположения самого скрипта (`SCRIPT_DIR/OpenSupaplex`), а не от
текущей папки. Поэтому скрипт можно запускать откуда угодно.

`TOOL_NAME` учитывает ОС: на Windows это `supaplex-dataset.exe`, на Linux/macOS — без расширения
(если собрать утилиту там).

## 4. Чтение сырого файла: step_dtype и read_spds

### step_dtype — шаг как numpy-структура

[Строки 66–75](supaplex_dataset.py#L66-L75). Все шаги в файле одного размера, поэтому их можно
описать одним структурным `dtype` и прочитать весь файл как массив, без цикла по байтам:

```python
("frame", "<u4")                          # uint32 little endian
("action", "u1"), ("flags", "u1"), ...    # по байту
("murphy", "<u2"), ("reserved", "<u2")    # uint16
("grid", "u1", (24, 60, 2))               # 2880 байт сразу как массив [y, x, (tile|state)]
("screen", "u1", (200, 320))              # 64000 байт, только если файл собран с экраном
```

Порядок и размеры полей обязаны совпадать с тем, что пишет `flushPendingStep` в C-утилите:
12 байт заголовка шага, затем сетка, затем экран.

### read_spds — файл в словарь

[Строки 78–124](supaplex_dataset.py#L78-L124). По шагам:

1. **Заголовок и концовка** ([80–84](supaplex_dataset.py#L80-L84)). Читаются первые
   `FILE_HEADER_SIZE` байт и последние 9.
2. **Проверки** ([86–97](supaplex_dataset.py#L86-L97)):
   - магические строки `SPDS` в начале и `SEND` в конце. Если `SEND` нет, утилита упала посреди
     записи, и файл неполный;
   - версия формата = 1;
   - размер файла точно равен `заголовок + число_шагов × размер_шага + концовка`. Это ловит
     несовпадение формата между C и Python.
3. **Шаги через `np.memmap`** ([99](supaplex_dataset.py#L99)). Файл не читается целиком в память
   заранее: numpy отображает его на массив структур `steps`, и поля берутся как столбцы
   (`steps["action"]`, `steps["grid"]` …).
4. **Уровень, палитра, имя** ([100–102](supaplex_dataset.py#L100-L102)). Это срезы заголовка.
   Имя уровня лежит в байтах 1446–1468 уровня в виде `"----- WARM UP -----"`; дефисы и пробелы
   по краям обрезаются. `.copy()` нужен, потому что `np.frombuffer` возвращает массив только для чтения,
   привязанный к буферу `header`.
5. **Словарь эпизода** ([104–122](supaplex_dataset.py#L104-L122)):
   - `tiles` и `states` — это `grid[..., 0]` и `grid[..., 1]`: последняя ось сетки разделяется на два массива;
   - **`murphy_xy`** ([112](supaplex_dataset.py#L112)). Игра хранит позицию Мёрфи одним числом —
     индексом клетки `y * 60 + x`. Здесь оно раскладывается обратно:
     `x = murphy % 60`, `y = murphy // 60`. Результат — массив `(T, 2)` со столбцами `(x, y)`,
     поэтому `tiles[t][y, x]` — это клетка, где стоит Мёрфи. Перед делением индекс приводится к
     `int32`, чтобы не было переполнения `uint16`, в конце — к компактному `int16`;
   - `failed` / `completed` / `gravity` — отдельные биты байта `flags` (`& 1`, `& 2`, `& 4`);
   - `level_name` и `solved` — скаляры, обёрнутые в `np.array(...)`, чтобы `np.savez` мог их сохранить.
6. **`np.array(steps[...])`** делает копию столбца из memmap в обычную память. После этого
   `del steps` закрывает отображение файла. Это важно на Windows: файл, открытый через memmap,
   нельзя удалить, а `build_one` сразу удаляет временный `.spds`.

Учтите, что `screens` копируется в память целиком: 10 000 шагов × 64 000 байт ≈ 640 МБ на время
сборки одного эпизода.

## 5. Загрузка эпизода: load_episode

[Строки 127–130](supaplex_dataset.py#L127-L130).

```python
with np.load(path, allow_pickle=False) as data:
    return {key: data[key] for key in data.files}
```

- `allow_pickle=False` — защита: `.npz` из чужих источников не сможет выполнить код при загрузке.
  Все поля — обычные массивы, строки сохранены как numpy-строки, pickle не нужен.
- `with` закрывает файл. Словарь сразу заполняется настоящими массивами (`data[key]` распаковывает поле).
- Ключа `screens` нет, если эпизод собирали с `--no-screen`. Код обучения должен это учитывать.

## 6. Сборка датасета

### find_demos — список демо

[Строки 134–149](supaplex_dataset.py#L134-L149). Каждый аргумент может быть:

- **папкой** — внутри рекурсивно ищутся `*.sp` и `*.SP`;
- **маской** (`demos\*.SP`) — раскрывается через `glob`;
- **путём к файлу** — если `glob` ничего не нашёл, путь берётся как есть, и ошибка «файл не найден»
  появится позже, в отчёте по этому демо.

На Windows файловая система не различает регистр, поэтому `*.sp` и `*.SP` находят одни и те же
файлы. Дубликаты убираются по нормализованному пути `os.path.normcase(os.path.abspath(...))`.
Результат сортируется, чтобы порядок не зависел от ОС.

### episode_name — имя выходного файла

[Строки 152–157](supaplex_dataset.py#L152-L157). Имя `.npz` строится из пути демо относительно
общей папки всех входных демо (`root`):

```
root = D:\...\solves
D:\...\solves\05\05s057-1.sp  →  05__05s057-1.npz
```

Разделители папок заменяются на `__`, все символы, кроме букв, цифр и `-_.`, — на `_`. Так демо с
одинаковыми именами из разных папок не перезаписывают друг друга. Если демо одно (`root = None`),
берётся просто имя файла.

### build_one — одно демо

[Строки 160–177](supaplex_dataset.py#L160-L177).

1. Создаётся временный файл `.spds` рядом с выходным `.npz` (`tempfile.mkstemp`). Дескриптор сразу
   закрывается: файл будет писать утилита.
2. Утилита запускается с `cwd=game_dir`. Это обязательно: движок ищет `FIXED.DAT`, `MOVING.DAT` и др.
   в текущей папке. Поэтому путь к демо передаётся абсолютным.
3. Коды возврата 0 (решён) и 1 (не решён) — нормальный результат: неудачные демо тоже сохраняются,
   с `solved = False`. Всё остальное, а также пустой файл, — ошибка утилиты.
4. `read_spds` → добавляется поле `source` (путь к демо) → `np.savez_compressed`. Экран почти весь
   состоит из повторяющихся тайлов, поэтому сжимается в десятки раз.
5. Временный файл удаляется в `finally` при любом исходе.
6. Любое исключение ловится и превращается в строку отчёта. Одно битое демо не останавливает
   сборку остальных.

Функция возвращает кортеж `(demo, out_path или None, сообщение)`.

### command_build — вся сборка

[Строки 180–213](supaplex_dataset.py#L180-L213).

1. Проверяет, что утилита есть в `--game-dir`.
2. Находит демо, вычисляет `root` как общий префикс путей (`os.path.commonpath`). Если демо одно,
   `commonpath` вернул бы сам файл, поэтому такой случай обработан отдельно.
3. При `--skip-existing` пропускает демо, для которых `.npz` уже есть.
4. Запускает `build_one` в `ThreadPoolExecutor` на `--jobs` потоков. Потоков, а не процессов,
   достаточно: основная работа идёт во внешнем процессе утилиты, а сжатие в `savez_compressed`
   (zlib) отпускает GIL.
5. Результаты выводятся в порядке входного списка (`futures` перебираются по порядку), а не по
   времени готовности.
6. Код возврата 0 — все демо обработаны, 1 — были ошибки.

## 7. Команды info и preview

### command_info

[Строки 216–228](supaplex_dataset.py#L216-L228). Печатает имя уровня, решён ли он, число шагов
(и примерное время: 35 шагов = 1 секунда игры), есть ли экран, сколько раз встречается каждое
действие и формы всех массивов.

`np.minimum(actions, len(ACTION_NAMES))` сводит любые неожиданные коды (> 9) в одну корзину
`other`, чтобы `bincount` и подписи не падали на старых файлах.

### command_preview

[Строки 231–261](supaplex_dataset.py#L231-L261).

- Перевод кадра в цвет — одна операция: `palette[screens[t]]`. Массив индексов `(200, 320)`
  используется как индекс в палитре `(16, 3)`, получается `(200, 320, 3)` RGB.
- Кадр увеличивается в 2 раза без сглаживания (`NEAREST`), в левом верхнем углу подписываются номер
  шага и действие.
- Берётся каждый `--every`-й кадр, не больше `--max-frames` штук, начиная с `--start`.
- Для `.gif` длительность кадра `1000 * every / 35` мс — анимация идёт с реальной скоростью игры.
  Для другого расширения сохраняется только первый кадр.

## 8. Точка входа main

[Строки 264–288](supaplex_dataset.py#L264-L288). Три подкоманды `argparse` (`build`, `info`,
`preview`) и словарь «имя команды → функция». Функции возвращают код возврата, он уходит в
`sys.exit`. Поэтому скрипт удобно вызывать из других скриптов и проверять результат.

По умолчанию `--jobs` — половина ядер процессора: каждый процесс утилиты держит в памяти кадры
своего эпизода.

## 9. Как добавить новое поле в датасет

Пример: сохранять номер кадра анимации Мёрфи.

1. **C-утилита** (`tools\supaplex-dataset.c`):
   - увеличить `kStepHeaderSize` (например, до 14) и записать значение в `captureObservation()`,
     например `writeUInt16(header + 12, gCurrentMurphyAnimation.currentFrame)`;
   - поднять версию в `writeFileHeader()` (`writeUInt16(header + 4, 2)`);
   - пересобрать: `bash windows/build-local.sh tools` и скопировать exe в `OpenSupaplex\`.
2. **Python** (`supaplex_dataset.py`):
   - добавить поле в `step_dtype` в том же месте и того же размера: `("murphy_frame", "<u2")` после `reserved`;
   - в `read_spds` принять версию 2 (и, если нужно, по-прежнему читать версию 1);
   - добавить в словарь эпизода: `"murphy_frame": np.array(steps["murphy_frame"])`.
3. Пересобрать датасет: старые `.npz` нового поля не содержат.

Проверка размера файла в `read_spds` сразу покажет ошибку, если формат в C и Python разошёлся.

## 10. Тонкие места

- **Наблюдение и действие одного кадра.** `screens[t]` — это кадр, нарисованный в конце шага `t-1`,
  то есть то, что игрок видел, принимая решение `actions[t]`. Результат действия виден в `screens[t+1]`.
  Для `t = 0` кадр — начальный вид уровня.
- **Код действия 15 в конце демо.** Дойдя до байта-терминатора `0xFF`, игра на последнем кадре
  кладёт во ввод `0xFF & 0xF = 15`. Это не нажатие, поэтому утилита пишет его как 0. В эпизодах,
  собранных до этого исправления, может встретиться 15; `info` и `preview` такое переживают.
- **Служебные значения тайлов.** Во время движения игра помечает клетки особыми кодами
  (например, 136, 153, 170, 187, 255) и превращает взрыв в 31. В `tiles` они остаются как есть: это
  часть реального состояния.
- **Флаг `failed`** означает «уровень завершается неудачей»: Мёрфи погиб, и идёт обратный отсчёт до
  выхода. Он остаётся `True` до конца эпизода.
- **Часы на панели** в `screens` стоят на нуле: в игре они тикают от таймера реального времени, а
  утилита проигрывает демо быстрее. На логику игры это не влияет.
- **Детерминизм.** Одно и то же демо всегда даёт бит в бит тот же эпизод: игра детерминирована, а
  ГСЧ «багов» стартует с сида, записанного в демо.
